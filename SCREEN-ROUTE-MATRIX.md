# SCREEN-ROUTE-MATRIX

The canonical inventory of **every screen this Flutter client registers a route
for**, read off `flutter_app/lib/core/router/app_router.dart` through 2026-09-16
(Point 19). One row per route.

## How to use it

- **It is an inventory, not an explanation.** Why a screen behaves as it does
  lives in `HANDOFF.md`; what the backend owes it lives in `DATA-NEEDS.md` and
  `API_CONTRACT.md`; who may open it lives in `CAPABILITIES.md`. This file
  answers *what exists, at which path, for which audience, and in what state* —
  and nothing else, so it can be updated incrementally instead of rewritten.
- **Update it in the same change that adds or moves a route.** A Point that
  adds screens adds rows; a Point that fills a placeholder edits that row's
  *Existing* and *Repository* cells. Nothing else in this file should move.
- **MISSING / PLANNED rows are marked as such and carry no implementation
  claim.** They exist where a route family is already designed (Points 5–13) so
  the later work has a place to land rather than a table to reconstruct.

## Column meanings

| Column | Means |
| --- | --- |
| Audience | **Common** (pre-session / any account) · **Tenant** (`main_admin`, `admin`) · **Platform** (`super_admin`) |
| Product Surface | Which shell hosts it: *Tenant shell* (`MainShell`), *Platform shell* (`PlatformShell`), *Root* (covers both / no shell), *Startup-only* (the classifier's own destinations) |
| Required Role | The **surface** gate, decided once by `resolveStartup` |
| Required Capability | The **authorization** gate on the route itself (`CAPABILITIES.md` §1). "—" means the route carries none |
| Repository / Data Source | What the screen actually reads |
| Backend Endpoint Later | The API family that will replace the mock. "—" means the screen needs none |
| Loading / Empty / Offline / Error / Permission | The screen's designed state for each. **n/a** = the screen reads nothing, so the state cannot occur |
| Mock/Dev Inspectability | How the state can be reached in a debug build without a backend |
| Test Status | The test file that covers it |

## 5. Gaps found while compiling this inventory

Recorded, not fixed — each belongs to a Point that owns it.

1. **Platform notifications have no route.** `/notifications` is the tenant
   centre and is deliberately outside the platform shell. A platform inbox
   (new demo account, security, subscription, health) is a later Point and will
   be a separate destination inside Operations, not a reuse of this one.
2. **Tenant notification preferences are tenant-shaped.** Their four toggles
   are shifts, stock, workshops and join requests, so there is no platform
   equivalent to expose and none was invented.
3. **`/more/performance` and `/more/org` are redirects with no screen.**
   Correct today, but they are the rows in this table whose *route* and
   *screen* are not one-to-one.
4. **Two screens are still marked "stub" in `DATA-NEEDS.md` §2.3/§2.4** while
   being fully routed here (shift, storage, workshop editors). The stub marking
   refers to their data, not their existence.
6. **Onboarding is production (Point 17B, closed in Point 17C).** `/signup`,
   `/verify-email`, `/link-team` and `/account-setup` are real forms, not
   holding pages. Google goes through `GoogleSdkIdentityGateway`
   (`google_sign_in ^7.2.0`); a build without `MTM_GOOGLE_SERVER_CLIENT_ID`
   shows the retryable "unavailable" answer, and debug builds keep the in-app
   mock chooser. Journey credentials survive a relaunch through
   `flutter_secure_storage` (`SecureAuthStateStore`). `/link-team` gives an
   invited Simple Admin who lands there a "check for my invitation" action
   instead of a Team Code dead end. No `/reset-password` family was added: the
   existing `/forgot` → `/otp` → `/new-password` flow is the reset flow. No
   route was added or moved by Point 17C.
7. **Point 18B added no route.** The Team/Demo decision is a state of
   `/link-team` (so the startup classifier and its invitation precedence are
   unchanged), `/login` changed presentation only, and the Simple Admin
   management routes are unchanged (capabilities are now grouped by module
   and each account row states its grant count).
